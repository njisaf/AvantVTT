---

## 1) Intent

Define a single, authoritative error taxonomy and the **AvantError** contract used across engine, adapter, and UI. Provide stable error codes, i18n message keys, JSON serialization, and UI‑mapping policy. All specs with validation rules (V‑xx) must map to a code in this catalog.

**Out‑of‑scope:** User copy text; adapter‑specific string wording (lives in i18n).

---

## 2) Naming & taxonomy

**Error code format:** `E_<AREA>_<NAME>` (UPPER\_SNAKE\_CASE)

**Areas (seed):**

* `CORE` – core engine invariants (e.g., CT invalid)
* `DICE` – dice parsing/evaluation
* `MODS` – modifiers & stacking
* `SCHEMA` – schema/validation failures
* `ENGINE` – rule violations not caught earlier
* `RUNTIME` – state desync / unexpected runtime conditions
* `DEV` – not implemented / development placeholders
* `IO` – file/content read/write issues (packs)

**Examples:** `E_DICE_EXPR`, `E_CORE_CT_INVALID`, `E_MODS_TYPE_UNKNOWN`, `E_SCHEMA_VALIDATION`.

---

## 3) Error object contract (normative)

TypeScript baseline:

```ts
/** @spec 00.3 */
export type Severity = 'error' | 'warn' | 'info';

/** @spec 00.3 */
export interface AvantErrorJSON {
  code: string;              // e.g., 'E_DICE_EXPR'
  messageKey: string;        // e.g., 'errors.dice.invalidExpression'
  details?: Record<string, unknown>; // structured context (safe)
  severity: Severity;        // error | warn | info
  cause?: { code?: string; message?: string }; // shallow summary only
  ts: string;                // ISO timestamp
}

/** @spec 00.3 */
export class AvantError extends Error {
  code: string;
  messageKey: string;
  details?: Record<string, unknown>;
  severity: Severity;
  cause?: unknown;
  constructor(code: string, messageKey: string, details?: Record<string, unknown>, severity: Severity = 'error', cause?: unknown);
  toJSON(): AvantErrorJSON;  // MUST be stable & lossless for the above fields
}
```

**R-00.3-01:** `AvantError.toJSON()` **MUST** be stable and omit stack traces by default.
**R-00.3-02:** Engine code **MUST NOT** construct ad‑hoc `Error` with raw strings for user‑visible paths; use `AvantError`.
**R-00.3-03:** `details` **MUST** contain only safe, non‑PII debug context.

---

## 4) i18n & messages

* `messageKey` points to adapter/UI bundles (e.g., `errors.dice.invalidExpression`).
* UI **MUST NOT** display developer strings; it renders an i18n string using `messageKey` and may include sanitized `details` tokens.

---

## 5) Throw vs return policy

* **Engine (pure functions):** On invalid inputs or invariant violations, **throw** `AvantError` with a specific code. Do **not** return Result types in engine core.
* **Adapter/UI layers:** Catch, map severity → UI channel (toast/banner/log), and surface localized copy; never swallow silently.
* **Schema validators:** Prefer returning a typed Result for bulk validation **OR** throw `E_SCHEMA_VALIDATION` with a structured list of issues; choose one consistently per validator module and document it.

---

## 6) Severity mapping policy (adapter guidance)

* `error` → blocking path; show `ui.notifications.error` (Foundry) and log at error level.
* `warn` → non‑blocking; `ui.notifications.warn` and console warn.
* `info` → log only or subtle banner; no user interruption.

## 8) Serialization & telemetry

* Errors included in logs and chat flags as `AvantErrorJSON`.
* Telemetry (if enabled) redacts `details` fields not explicitly whitelisted by the emitting module.

---

## 9) Acceptance Criteria (AC)

**AC-00.3-01** Every V‑rule in shipped specs maps to a defined error code in this catalog.
**AC-00.3-02** `AvantError` serializes/deserializes losslessly to `AvantErrorJSON`.
**AC-00.3-03** UI never renders raw developer strings; only `messageKey` + safe tokens.
**AC-00.3-04** Adapter maps severity to UI channel per §6 (tested).
**AC-00.3-05** Engine unit tests assert throws for 01.1 V‑01..V‑03 with the correct codes.
**AC-00.3-06** Error codes are **stable**; deprecations are versioned and documented.

---

## 10) Test plan

* **Unit:** constructor, `toJSON`, and round‑trip; throwing sites in 01.1.
* **Adapter:** severity→UI mapping harness; i18n rendering with token substitution.
* **Golden:** snapshot representative thrown errors from engine functions.

---

## 11) Change management & deprecation

* Codes are **append‑only**; do not repurpose.
* On deprecation, keep the code and document a successor; continue to render a compatible `messageKey`.
* Maintain a `CODES.md` autogenerated table from the catalog for quick reference.

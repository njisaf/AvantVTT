# Spec 03.1 — Actor Model (Ready Draft)

**Spec ID:** 03.1
**Status:** Ready Draft
**Source of Truth:** *Avant PHB v1.md* (mechanics only)
**Path:** `docs/specs/03-data/03.1-actor-model.md`
**Linked Specs:** 01.1 Task Resolution; 01.3 Thresholds & Defences; 02.2 Action Economy; 03.5 Talent Schema; 00.3 Error Catalog

---

## 1) Intent

Define the canonical, validated data model for **Actors** (PCs, NPCs, Hazards) used by the engine and the Foundry adapter. Specify fields, invariants, and derivations required to run core rules with zero UI coupling.

Out of scope: setting/lore; sheet layout; styling.

---

## 2) Core concepts (from PHB)

* **Attributes (4):** Focus, Grace, Intellect, Might — integer **modifiers** (not ability scores).
* **Expertise:** per-skill/gear point allocations; max per ability = `floor(level/2)` with a minimum of 1.
* **Defence Threshold (DT):** `11 + total relevant gear modifier`.
* **Action Points (AP):** handled in 02.2; stored on the actor for turn bookkeeping.
* **Power Points (PP):** resource for augmentations; per-level **Max PP** and per‑power **PP Limit** come from the Level Table.
* **Fortune Points:** 0–5; spent to reroll dice (01.1/05.2 flows).

## 3) TypeScript model (normative)

```ts
/** @spec 03.1 */
export type AttributeKey = 'focus' | 'grace' | 'intellect' | 'might';

/**@spec 03.1*/
export interface AttributeBlock {
  focus: number;     // int; see bounds R-03.1-05
  grace: number;     // int
  intellect: number; // int
  might: number;     // int
}

/**@spec 03.1*/
export interface SkillEntry {
  id: string;                // canonical skill id (e.g., 'perception')
  attribute: AttributeKey;   // attribute used for this skill
  expertise: number;         // points allocated; bounds R-03.1-06
  bonuses?: Record<string, number>; // typed bonuses by id; stacking per 01.4
}

/**@spec 03.1*/
export interface GearModifier {
  id: string;                // item or effect id
  kind: 'nimble'|'adept'|'heavy'|'spiritual'|'misc'; // category used by DT rules
  value: number;             // signed; stacking per 01.4
}

/**@spec 03.1*/
export interface PowerPoints {
  current: number;           // 0..max; see R-03.1-08
  max: number;               // from Level Table
  perPowerLimit: number;     // from Level Table (PP Limit)
}

/**@spec 03.1*/
export interface ActorResources {
  ap?: number;               // per-turn budget (02.2 governs defaults)
  fortune: number;           // 0..5
  power: PowerPoints;        // PP pool
}

/**@spec 03.1*/
export interface ConditionState { id: string; intensity?: number; duration?: string; }

/**@spec 03.1*/
export interface AvantActorData {
  id: string;                // document id
  name: string;
  kind: 'pc'|'npc'|'hazard';
  level: number;             // 1..20
  ancestryId?: string;
  cultureId?: string;
  vocationId?: string;

  attributes: AttributeBlock;   // modifiers only
  skills: Record<string, SkillEntry>; // normalized map, not array in storage

  gearMods: GearModifier[];     // inputs to DT computation
  thresholds: {
    dt?: number;                // derived by 01.3; optional cache
  };

  resources: ActorResources;
  speeds?: Record<string, number>; // e.g., { land: 25 }
  hp?: { current: number; max: number }; // hazards/pcs; exact calc lives in 03.x

  conditions?: ConditionState[];
  flags?: Record<string, unknown>; // extension surface
}
```

### 3.1) Runtime schema

Use a runtime validator (e.g., zod) that enforces the invariants in §4 and returns **E\_SCHEMA\_VALIDATION** with a structured `issues[]` list.

---

## 4) Invariants & rules (normative)

**R-03.1-01** Level **MUST** be an integer in `1..20`.

**R-03.1-02** `kind` determines available fields: hazards may omit skills but must provide any stats used by their actions.

**R-03.1-03** `thresholds.dt` **MUST** be computed as `11 + totalRelevantGearModifier` (see 01.3 for relevance rules). Caches **MUST** be invalidated when `gearMods` or applicable conditions change.

**R-03.1-04** Attribute modifiers are integers. Initial modifiers start at `+0` before ancestry/culture/vocation adjustments. Maxima by level follow PHB: at level 1, max `+3`; eventual cap `+5`, after which each increase counts as 0.5 (rounded down).

**R-03.1-05** Attribute modifiers **SHOULD** be within `-5..10` for validation sanity (PHB guidance); higher allowed if explicitly unlocked by effects.

**R-03.1-06** For each `SkillEntry`, `expertise` **MUST** satisfy `1 <= expertise <= floor(level/2)`.

**R-03.1-07** `resources.fortune` **MUST** be an integer `0..5`.

**R-03.1-08** `resources.power.current` **MUST** be `0..resources.power.max`. `resources.power.perPowerLimit` **MUST** be `>= 1` and match the Level Table for the actor’s level.

**R-03.1-09** `skills[*].attribute` **MUST** reference an existing key in `attributes`.

**R-03.1-10** `gearMods[*].kind` **MUST** be one of the enumerated kinds; unknown kinds **MUST** throw `E_SCHEMA_VALIDATION`.

## 5) Computations

```ts
/** @spec 03.1 */
export function computeDT(actor: Pick<AvantActorData,'gearMods'>): number {
  const totalRelevant = sumRelevantGear(actor.gearMods); // see 01.3 relevance
  return 11 + totalRelevant;
}

/** @spec 03.1 */
export function maxExpertiseAt(level: number): number {
  return Math.max(1, Math.floor(level / 2));
}
```

---

## 6) Acceptance Criteria (AC)

**AC-03.1-01** Given a level‑1 PC with `attributes` set and an empty `gearMods`, `computeDT` returns **11**.

**AC-03.1-02** At level 7, `maxExpertiseAt(7) === 3`; schema rejects a skill with `expertise: 4`.

**AC-03.1-03** Setting `resources.fortune` outside `0..5` yields `E_SCHEMA_VALIDATION` with `{ path: 'resources.fortune' }`.

**AC-03.1-04** `resources.power.max` and `perPowerLimit` match the Level Table for the provided level; mismatches are rejected with `E_SCHEMA_VALIDATION`.

**AC-03.1-05** Updating `gearMods` invalidates any cached `thresholds.dt` and recomputation produces the expected value.

**AC-03.1-06** Skills reference a valid `attribute`; invalid references are rejected.

## 7) Examples
